# Assumptions & decisions

Ambiguities in the build plan and how they were resolved. Newest phase last.

## Phase 1 — Foundation

| # | Topic | Decision | Why |
|---|---|---|---|
| 1 | Local infra | **No local Postgres/Docker.** Dev and prod both use hosted **Neon** (Postgres + pgvector). The plan's "Docker Compose for local dev" is replaced; Compose returns in Phase 12 only for the deploy VM (FastAPI + n8n + Caddy). | Owner asked for a deployable setup without local services; Docker isn't installed. |
| 2 | Neon connection string | One variable, `DATABASE_URL`, holding Neon's **direct** (non `-pooler`) string exactly as Neon gives it. `app.config.to_async_url` converts it for asyncpg (`postgresql+asyncpg://`, `sslmode=require` → `ssl=True`, drops `channel_binding`). Alembic uses the same function. LangGraph's psycopg checkpointer (Phase 6) will derive its URL from the same value. | Avoids three copies of the same secret drifting apart; asyncpg prepared-statement caching conflicts with PgBouncer transaction pooling. |
| 3 | API key placement | The browser never sees `API_KEY`. Client components call `/api/backend/*`, a Next.js route handler that adds `X-API-Key` and streams the response (SSE-ready). Server env is `API_URL` + `API_KEY` (plan named `NEXT_PUBLIC_API_URL`; a public URL isn't needed with the proxy). | Plan requires the key be server-side only. |
| 4 | shadcn/ui | Primitives (`Button`, `Card`, badges) are written in shadcn's style (cva + `cn`, Radix `Slot`) and restyled per §13b, rather than generated by the shadcn CLI. More shadcn components can be added later as needed. | The §13b restyle replaces nearly all default styling anyway. |
| 5 | GSTIN in mockups | The mockup shows `29AABCT1332L1ZV`, which fails the GSTIN checksum. Seed data uses the checksum-valid `29AABCT1332L1ZA` for the same PAN. | Plan requires valid checksums; validation would otherwise flag our own vendor. |
| 6 | Seed data | Generated deterministically by `backend/scripts/build_seed_data.py` → `data/seed/*.json`; loaded by `scripts/seed.py` (replaces reference tables). Edge-case hooks: TechNova PO-2026-0042 at ₹1,100/unit (contract-rate case), BlueLeaf PO-2026-0035 with no GRN (ON_HOLD), Sharma PO-2026-0038 (split invoicing), CloudNest non-PO history coded to GL 6420 / CC-IT-01 (5 cases), Zenith Traders BLOCKED, Rangoli Packaging bank ••••6634 (bank-change case). | Reproducible demo data; fixtures for later phases. |
| 7 | Company GST state | Acme Retail Pvt Ltd is registered in Karnataka (29): Karnataka vendors charge CGST+SGST, others IGST. | From the plan's "Bengaluru". |
| 8 | Python toolchain on Windows | Python 3.12 via uv. The virtualenv is kept at `C:/Users/asus/.venvs/invoiceiq` (`UV_PROJECT_ENVIRONMENT`) — compiled extensions failed to load from a long project path (Windows MAX_PATH). Frontend uses `node-linker=hoisted` (`frontend/.npmrc`) for the same reason. | Windows path-length limits. |
| 9 | Later-phase pages | Sidebar routes that belong to later phases render a "Arrives in phase N" placeholder so navigation never 404s. | Keeps the shell complete and demoable. |

## Phase 2 — Test data & knowledge base

| # | Topic | Decision | Why |
|---|---|---|---|
| 10 | PDF tooling | Invoices are drawn with **ReportLab** (dev dependency) and "scanned" with **PyMuPDF** + **Pillow** (rasterise → greyscale → skew → noise/speckles → blur → low-quality JPEG → image-only PDF). PyMuPDF and Pillow are runtime dependencies because Phase 3 uses them for text-layer detection and page images. ReportLab has no type hints, so mypy ignores its imports; PyMuPDF calls are excluded from the untyped-call check. | Pure Python, works on Windows and ARM Linux, no system packages (wkhtmltopdf/Chrome). |
| 11 | Rupee sign | Documents print **"Rs." / "INR"** instead of ₹ — the built-in PDF fonts have no ₹ glyph, and many real Indian invoices do the same. Extraction must normalise both. Knowledge-base docs (Markdown) use ₹. | Avoids bundling a TTF font; realistic. |
| 12 | Seed additions | Added GRN-0315…0321 (so the clean cases on PO-2026-0045…0049 can 3-way match) and PO-2026-0050 (Kaveri, catalogue) / PO-2026-0051 (Malabar, cabinets) with GRNs, for the IGST-error and math-error cases. Neon was reseeded. Existing edge-case hooks (PO-2026-0035 has no GRN, etc.) are unchanged. | Each test invoice needs its own PO so cases don't interfere. |
| 13 | Case specs are code | Every test document is a spec in `backend/scripts/invoice_specs.py` (lines, vendor, printed deviations, expected outcome). Amounts are computed from lines, so ground truth can't drift from the PDF; a test fails if the committed PDFs/JSON are stale. | Single source of truth for Phase 3 fixtures, Phase 4 rule tests and Phase 11 eval. |
| 14 | `expected.decision` meaning | The decision **before any human acts**. An approval gate (amount > ₹5 lakh, non-PO invoice) gives `NEEDS_REVIEW` with `approvals` listing the roles; `final_decision` is the outcome once the intended human action happens. Touchless `APPROVED` means no gate fired (policy §9). | Plan says "amount > approval limit → NEEDS_REVIEW"; applied the same rule to the non-PO approval. |
| 15 | Outcomes the plan left open | Unknown supplier (valid GSTIN, not in master) → `ON_HOLD` (missing master data; the agent may not create vendors). Blocked vendor → `REJECTED`. Arithmetic off by > ₹1 → `REJECTED` (vendor must reissue). Quotation and credit note → `REJECTED` (credit notes are adjusted against the original, not paid). Wrong GST head (IGST intra-state) → `NEEDS_REVIEW` for the tax team. Split invoice #3 raises both `OVER_PO_BALANCE` and `QTY_VARIANCE` (340 reams billed vs 300 ordered/received). | Encoded in `ap-policy.md` so the rules and their citations agree. |
| 16 | ERP read-back case | `malabar-erp-mismatch` passes every rule; its ground truth carries `erp_fault: amount_minus_one_paisa`, which the mock ERP (Phase 8) will honour in demo mode so the read-back check fails. Proposed exception category for this: `ERP_MISMATCH` (not in the plan's list). | The fault is in the ERP, not the PDF, so it has to be injected. |
| 17 | Policy numbers | Price tolerance 2% per line and ₹5,000 per invoice; quantity tolerance 0; freight ≤ ₹1,000; duplicate window 30 days; approval matrix ≤ ₹5 L none, ≤ ₹25 L Finance Manager, above that + CFO; non-PO → Department Head (+ Finance Manager above ₹1 L); bank change → AP Manager + Finance Controller. These are the defaults the Phase 8 Operating Procedure will start from. | Plan gave examples, not values. |
| 18 | Recurring invoices vs duplicate window | CloudNest bills the same ₹49,560 every month. Oct 1 → Nov 1 is 31 days, just outside the 30-day window. Phase 4's suspected-duplicate rule should also compare service periods so monthly subscriptions aren't flagged. | Noted now so the rule isn't written naively. |
| 19 | Knowledge base format | Markdown with YAML front matter (`doc_type`, `vendor_id`, `valid_from/valid_to`, …) and numbered `##`/`###` headings, so `MarkdownHeaderTextSplitter` yields citable sections like `[contracts/technova §2.1]`. Contracts include mid-year rate amendments (Sharma paper, BlueLeaf line haul, Rangoli boxes) and one terminated contract (Zenith). A test checks that every citation in the ground truth resolves to a real section. | Grounded citations in Phase 5. |

## Phase 3 — Extraction

| # | Topic | Decision | Why |
|---|---|---|---|
| 20 | Models | Defaults `gemini-3.5-flash` (primary), `gemini-3.5-flash-lite` (fallback), Groq `openai/gpt-oss-120b` (text fallback) — all overridable in `.env`. Versions: `langchain-core` 1.8.2, `langchain-google-genai` 4.5.0, `langchain-groq` 1.2.0 (APIs checked against the installed sources). | Current free-tier models at build time; names change often, so they're config. |
| 21 | Fallback order | Text PDFs: primary provider → the other provider → Gemini lite. Scanned PDFs: Gemini → Gemini lite (Groq is text-only, per the plan). Missing keys → `LLMNotConfiguredError` naming the variable. | `.with_fallbacks()` over whichever providers have keys. |
| 22 | The LLM only reads | The schema (`app/llm/schemas.py`) asks for values **as printed** plus page, verbatim snippet and (for images) a 0–1000 box. Every GST row is read separately; CGST/SGST/IGST and tax totals are summed in Python. Normalisation (amounts, day-first dates, GSTIN, PO, state, IFSC) is pure Python. | Keeps arithmetic out of the model and makes every value checkable against the PDF. |
| 23 | Digital vs scanned | A page with ≥ 80 characters in its text layer is digital. Digital PDFs send the text layer (no image) — cheaper and lets Groq be a fallback. Scans send PNG pages at 170 dpi; at most 5 pages per document. | Plan §6 `document_check`. |
| 24 | Doc type | The model classifies; on digital PDFs a title keyword (TAX INVOICE / CREDIT NOTE / QUOTATION) overrides it, with a warning. | Titles are unambiguous; models occasionally call a quotation an invoice. |
| 25 | Confidence calibration | Self-reported LLM confidence is a starting point, then: found verbatim in the text layer → ≥ 0.95 (with a bbox); digital but not found → ≤ 0.6 (possible hallucination); unparseable → ≤ 0.2; GSTIN fixed by OCR substitution → ≤ 0.75; GSTIN checksum fails → ≤ 0.4; amounts that reconcile (lines → subtotal → total within ₹1) → ≥ 0.9; **scanned pages are capped at 0.55 + 0.4 × quality**, where quality (0–1) comes from edge sharpness and contrast. Generated scans: good ≈ 1.0 (cap 0.95), medium ≈ 0.74 (0.85), poor ≈ 0.33 (0.68 → `LOW_CONFIDENCE`). Threshold 0.8 over the key fields. | Makes the "low-quality scan → review" behaviour deterministic and explainable instead of depending on the model's mood. Constants live at the top of `extractor.py`. |
| 26 | Wrong totals | Extraction reports the total **as printed** even if it doesn't add up (`malabar-math-error`); deciding it's wrong is the rules engine's job (Phase 4). Arithmetic agreement only ever raises confidence, never lowers it. | "The AI extracts; the rules decide." |
| 27 | Retry | If a required field (vendor name, GSTIN, invoice number, date, total) is missing on an invoice, retry once with a stricter prompt naming the missing fields and fill gaps from the retry. | Plan §6 edges. |
| 28 | Evidence boxes | Digital: PyMuPDF `search_for` on the value as read, then printed variants (Indian grouping, date formats), then the snippet. Scans: Gemini's `box_2d` converted to PDF points (approximate). | Highlights on the PDF preview (plan §2b.2). |
| 29 | Tests without an LLM | A synthetic "perfect reader" built from ground truth runs the whole post-LLM pipeline on all 25 PDFs. Real model outputs are recorded with `scripts.eval_extraction --record` into `tests/fixtures/extraction/` and replayed by `test_recorded_extraction` (≥ 90% field accuracy). | CI never calls an LLM; recordings catch real-model drift. |
| 30 | First live results (2026-11-18) | All 25 test invoices: **100% field accuracy (560 fields)**; doc types all correct; poor scan min key confidence 0.68 → review, medium 0.85, good 0.95. Every case was answered by the **fallback** `gemini-3.5-flash-lite` because the primary returned 503 "high demand"; ~30 s per case was mostly spent retrying the primary. Fixtures in `tests/fixtures/extraction/` are these flash-lite readings. If the primary stays overloaded, set `GEMINI_MODEL=gemini-3.5-flash-lite` or `LLM_MAX_RETRIES=0` to cut latency (Phase 11 measures this properly). | Recorded so the numbers in EVAL_RESULTS.md (Phase 11) have a baseline. |

## Phase 4 — Rules engine

| # | Topic | Decision | Why |
|---|---|---|---|
| 31 | Layout | `app/rules/`: `models` (inputs/outputs), `policy` (numbers from #17 — what the Phase 8 procedure will version), `arithmetic` (doc type, required fields, confidence, math, dates — named so it doesn't shadow stdlib `math`), `tax` (GSTIN + CGST/SGST vs IGST + tax at line rates; kept out of `gst.py` because extraction imports that module), `vendor`, `matching` (PO, line and contract-rate matching), `tolerance`, `duplicates`, `approval`, `decide` (`evaluate()` + `history_record()`), `reference` (seed loader). Pure Python, no LLM, no I/O apart from the seed loader. | Plan §14; "the rules decide". |
| 32 | Staged evaluation | Stage 1 doc type → stage 2 fields/math/GST/vendor/exact duplicate → stage 3 suspected duplicate, PO, GRN, qty, price, PO balance → stage 4 approval gates. A reject in a stage (or an unknown vendor) stops later stages. Rejected cases carry no exceptions or approvals — rejection is final. | Matching a quotation or a blocked vendor's invoice against POs only adds noise. |
| 33 | Rule statuses | PASS / WARN / FAIL plus **SKIP** (not applicable: service PO with no GRN, no bank account printed). Each non-pass rule has a severity (`reject`/`hold`/`review`) that drives the precedence, and an optional exception category. Unknown vendor and blocked vendor have no category (none fits; ground truth expects none). Vendor name matching but GSTIN differing → `TAX_MISMATCH`. | Plan §6 `decide` precedence. |
| 34 | Missing contract rate | When no cited contract rate covers a line, the **PO rate** is the reference and the price rule still passes — not `WARN: no contract rate found` as plan §7 says. Policy §3.6 makes the PO the next source in the hierarchy; a WARN would send every line without a numeric rate (e.g. Northwind's "as quoted on the PO" labour) to review. A contract rate is only used when its validity covers the invoice date. | Avoids false reviews; still never invents a rate. |
| 35 | PO balance vs price tolerance | The balance check values the invoice at **PO prices** (qty × PO rate + PO tax). Otherwise a price variance inside tolerance (sharma-within-tolerance, +1.2%, ₹50,150 vs a ₹49,560 PO) would also be an `OVER_PO_BALANCE`. The reported excess is still invoice total − remaining. | Each variance reported once, by the rule that owns it. |
| 36 | PO consumption source | Remaining balance and cumulative quantities come from the **invoice history** (live invoices on the PO; `REJECTED`/`CANCELLED` excluded; pending ones count, so balance is reserved). `purchase_orders.amount_invoiced` is treated as a cache (it equals the seed history today). Seed invoices have no lines, so they count towards the amount but not quantities. | One source of truth; Phase 6 registers each case into the history. |
| 37 | Suspected duplicate vs PO balance | When a suspected duplicate is found, the PO balance and quantity checks **leave out the suspected original** — whether it is the same billing is exactly the question the duplicate exception asks. Otherwise northwind-suspect-duplicate would also raise `OVER_PO_BALANCE` and `QTY_VARIANCE`. Duplicates also compare service periods when both are known (#18). Invoice numbers are compared on letters and digits only. | One clear question per root cause. |
| 38 | Non-PO branch | No PO printed and no open PO of the vendor scores ≥ 0.75 → non-PO branch **if** the contract has a "no purchase order" clause or the vendor category is SaaS/Utilities/Rent/Professional services (policy §7.2). Coding = most common GL/cost centre on the vendor's reviewed (PAID/POSTED/APPROVED) invoices, with its basis; approver = that cost centre's Department Head (+ Finance Manager above ₹1 L). Otherwise `NO_PO`. | Plan §2b.6; never infer without evidence. |
| 39 | Exceptions carry the handoff | Each exception has owner role + name (buyer on the PO, GRN store, policy §7.4 names), variance, citations, recommendation and one specific question (plan §2b.4). Phase 8's `route_exception` adds recovery attempts on top. | Ready for the review UI. |
| 40 | Contract terms before RAG | Tests read `ContractTerms` (rates with validity, rate-revision and no-PO clauses, each cited) straight from the contract Markdown (`tests/contract_fixture.py`). Phase 5's retriever must produce the same model. Contract citations for tax/bank/termination clauses (kaveri §2.5, rangoli §5.1, blueleaf §2.5, zenith §2.2) and ERP (ap-policy §10.1) are deferred to Phases 5/8. | Plan §16 Phase 4 vs Phase 5. |
| 41 | Ground-truth typo | `sharma-split-3`'s reason said 340 reams billed in total; it is 320 (100 + 100 + 120). Fixed in `invoice_specs.py` and regenerated (PDF unchanged). | Data correctness. |
| 42 | Results | All 25 cases give the expected decision, exception categories, approvals, matched PO/GRN and coding, replaying the recorded extraction fixtures in manifest order (`tests/test_rules_cases.py`); every citation resolves to a real knowledge-base section. 129 new tests, 416 total. | Phase 4 "done when". |

## Phase 5 — RAG

| # | Topic | Decision | Why |
|---|---|---|---|
| 43 | Libraries | `langchain-postgres` 0.0.19 (`PGVectorStore` v2: table, upserts, filtered dense search), `langchain-text-splitters` 1.1.3, `fastembed` 0.9.1 (`BAAI/bge-small-en-v1.5`, 384-d, ~65 MB, cached in `~/.cache/fastembed`). The `pgvector` Python package is pinned to 0.3.6 (was 0.5.1) because `langchain-postgres` requires `<0.4`; nothing imported it. APIs checked against the installed sources. | Plan §3 stack; dependency compatibility. |
| 44 | Chunking & ids | Front matter → metadata; `MarkdownHeaderTextSplitter` on `#/##/###`, then 800/100 recursive split. The chunk text is prefixed with its heading path (doc title › section) so short sections embed with context. Citation = `<path> §<deepest numbered heading>`. Chunk id = hash of (source, section, part, text): re-indexing only adds/removes changed chunks. 191 chunks. | Plan §7; citable, idempotent. |
| 45 | Hybrid search | Dense via `PGVectorStore` (cosine), full-text via our own SQL on the same table's `content_tsv` (GIN index) with **OR-ed** terms (`to_tsquery('a | b')`), merged with RRF (k=60). `PGVectorStore`'s built-in hybrid uses `plainto_tsquery`, which ANDs every word and misses most natural-language questions, and its fusion drops the per-signal scores we need for the relevance gate. An in-memory store (exact cosine + BM25) implements the same interface for tests and offline eval. | Plan §7 "hybrid … RRF"; grounding threshold. |
| 46 | Relevance gate | A chunk is returned only if dense cosine ≥ 0.55 or full-text matched it. Off-topic queries (e.g. "recipe for chocolate cake", top cosine 0.52) return nothing, so callers can say "nothing found". | Plan §7 grounding rule. |
| 47 | Query glossary | Queries are expanded with a small AP glossary (goods received ↔ GRN, purchase order ↔ PO, GSTIN). Raised retrieval hit-rate@5 from 83% to 89% on the eval set. A broader "pay → reject/blocked" expansion was tried and removed as overfitting the eval. | Users ask in words; documents use acronyms. |
| 48 | Contract terms = retrieve → read → ground | Per invoice: one query per line ("agreed rate <description> HSN <code>") plus rate-revision, no-PO and payment-terms queries, filtered to `doc_type=contract` and the vendor. The LLM (same provider chain as extraction, `structured_model`) reads the excerpts into `ContractTermsRead`. Python then **grounds** it: a rate survives only if its cited excerpt was retrieved and contains that amount and those validity dates; a clause citation survives only if the excerpt's wording matches (e.g. a "no purchase order … raised" sentence); payment days must be stated. Everything dropped is listed with a reason. | First live run: the model cited Sharma §5.2 ("Invoices must quote the PO number") as a no-PO clause — grounding on numbers alone wasn't enough. |
| 49 | Fixtures | `scripts.eval_rag --record-contracts` saves, per test case with a known vendor (24), the retrieved citations and the model's reading to `tests/fixtures/contract_terms/`. Replay re-grounds the reading against the current knowledge base, so a contract edit that invalidates a recorded rate fails the tests. `test_rules_cases.py` now uses these instead of the Markdown parser; the parser (`tests/contract_fixture.py`) stays as the cross-check that RAG picks the same rate per invoice line. | CI never calls an LLM; plan §16 Phase 5 "done when". |
| 50 | RAG eval | 18 questions in `data/eval/rag-questions.json`, each with the sections that answer it and the facts a correct answer states. Retrieval is evaluated **unfiltered** (as Ask-AP would search). Answers: an LLM answers from the top 5, a second call judges fact coverage (contradiction = 0). The answering prompt is eval-only; the real assistant is Phase 9. Results in `docs/EVAL_RESULTS.md`. | Plan §7 RAG eval. |
| 51 | Knowledge API | `GET /knowledge` (documents, chunk counts, how many are indexed), `POST /knowledge/search` (hybrid search with optional vendor/doc-type filter — for the `/knowledge` page and debugging), `POST /admin/reindex`. All behind the API key. `scripts/ingest_knowledge.py` does the same re-index from the CLI. | Plan §11, §13 `/knowledge`. |
| 52 | Results (2026-11-18) | Neon index: 191 chunks, re-index idempotent. RAG eval: retrieval hit-rate@5 **89%** (16/18; misses: Deccan no-GRN clause, Zenith termination), MRR 0.80+; answer correctness **82%** (LLM judge; weakest: bank-change answer covering 1 of 3 facts, Zenith). Edge case #3 live on Neon: PRICE_VARIANCE, ₹1,250 vs contracted ₹1,100, cited `contracts/technova §2.1` + §2.5. Contract recordings: 9 by the primary Gemini/Groq chain, 15 with `GEMINI_MODEL=gemini-3.5-flash-lite` because the primary was slow (~90 s/case of 503 retries vs ~3 s). All 25 rule cases still match ground truth on RAG terms; 460 tests. | Phase 5 "done when". |

## Phase 6 — LangGraph pipeline + streaming

| # | Topic | Decision | Why |
|---|---|---|---|
| 53 | Versions | `langgraph` 1.2.22, `langgraph-checkpoint-postgres` 3.2.1 (APIs checked in the installed sources: `interrupt()`, `Command(resume=…)`, `get_stream_writer()`, `AsyncPostgresSaver`). FastAPI 0.163's native SSE (`EventSourceResponse` + `ServerSentEvent`) — no extra package. | Plan §3; check current APIs. |
| 54 | Nodes | `intake → document_check → extract → vendor_match → retrieve_policy → rules → register_case → human_review (only for NEEDS_REVIEW / ON_HOLD) → explain → close_case`. The plan's validate / po_match / duplicate_check / tolerance_check / decide stay **one `rules` node** calling the Phase 4 engine, which emits one `rule` event per check, so the timeline still shows every check without splitting a pure function into fake stages. `route_exception`, `approval_routing`, `post_erp`, `verify_post` and `non_po_checks` arrive in Phase 8. | Rules stay one deterministic, unit-tested function. |
| 55 | State & errors | State is plain JSON (model dumps), so any checkpointer can store it safely. Every node is wrapped: start/finish events with timings, and an exception becomes `failed` + `errors[]` → conditional edge to END → run FAILED with the message (never hangs). `interrupt()`'s `GraphBubbleUp` is re-raised, not treated as an error. | Plan §6 "never hang". |
| 56 | Case history | `register_case` upserts the run's row in `invoices` (source RUN, status = rules' decision) right after the rules, so a case waiting for review already reserves PO balance and counts for duplicates; `close_case` sets the final status. A rerun marks the earlier attempt `SUPERSEDED` (a dead status), so a rerun isn't an exact duplicate of itself. | ASSUMPTIONS #36; reruns. |
| 57 | Human review | `human_review` calls `interrupt(payload)` (headline question, exceptions with owner + question, approvals, low-confidence fields with page/bbox, citations). `POST /runs/{id}/review` resumes with `Command(resume={action, comment, reviewer})`: APPROVE → APPROVED, REJECT → REJECTED, REQUEST_INFO → pause again (the case keeps waiting; Phase 10's n8n emails the vendor). Approval-matrix gates use the same pause until Phase 8's approval routing; four-eyes is Phase 8. | Plan §6 nodes 12–13. |
| 58 | Explain | LLM summary (same provider chain, `ExplanationRead`) from the rule results, exceptions and cited clauses; citations it writes that weren't offered are stripped (also inside "[a, b]" lists). Any LLM failure → deterministic template. It never changes the decision. | Plan §6 node 16. |
| 59 | Runner | `RunService` drives `astream(stream_mode=["updates","custom"])` as an asyncio task per run: custom events → `run_steps` rows (seq-numbered) + in-process broker → SSE; updates → run row snapshot; `__interrupt__` → WAITING_REVIEW. SSE replays persisted steps after `?after=<seq>` then follows live (subscribe-then-read, dedup by seq; 15 s pings), so a page refresh restores the timeline. On startup, RUNNING/QUEUED runs resume from their checkpoint (`astream(None)`), or from scratch if none. Single API process; a queue/worker split is out of scope for the free-tier deploy. | Plan §6 streaming, "survive restarts". |
| 60 | Checkpointer | `AsyncPostgresSaver` over a psycopg `AsyncConnectionPool` on Neon's direct URL (`autocommit`, `prepare_threshold=0`, `check_connection` because Neon drops idle connections); `InMemorySaver` in tests or without Postgres. On Windows, psycopg can't use the Proactor event loop, so uvicorn runs with `--loop app.loop:selector_loop_factory` (README, `.claude/launch.json`); Linux is unaffected. | Found in the live check. |
| 61 | Files & API | Uploads stored content-addressed at `backend/var/uploads/<sha256>.pdf` (`STORAGE_DIR`; R2 in Phase 12). API: `POST /runs` (PDF ≤ 10 MB), `GET /runs`, `GET /runs/{id}` (steps, reviews, state, review request), `GET /runs/{id}/file`, `GET /runs/{id}/events` (SSE), `POST /runs/{id}/review`, `POST /runs/{id}/rerun`, `GET /samples`, `POST /samples/{key}/run`. Migration 0002: `runs`, `run_steps`, `reviews`, invoice-history columns. | Plan §10–11. |
| 62 | Live results (2026-11-18, Neon, flash-lite) | `deccan-scanned-poor`: paused at human_review after ~36 s (vision extract 15 s, contract retrieval + reading 15 s); **server restarted while paused**; APPROVE resumed from the Neon checkpoint → explain → COMPLETED/APPROVED. `technova-contract-rate`: paused with the "rate changed from ₹1,100 to ₹1,250?" question; REJECT → COMPLETED/REJECTED with a cited summary. `retrieve_policy` (~15 s) is the slowest step — Phase 7 needs samples < 30 s, so it should run the per-line queries concurrently or batch them. | Phase 6 "done when". |

## Phase 7 — Live run view, review queue, dashboard

| # | Topic | Decision | Why |
|---|---|---|---|
| 63 | Speed | `retrieve_policy` ran its 5–7 queries one after another, each two Neon round trips: now `asyncio.gather` across queries and across dense/sparse within a query (results merged in query order, so the excerpt set is unchanged and the recorded fixtures still apply). The embedding model loads in a background thread at startup. Store init and model load are guarded by locks against the concurrent first calls. 15 s → ~5–7 s (most of what's left is the LLM reading the clauses). | Phase 7 "< ~30 s per sample". |
| 64 | Fewer commits | The runner wrote and committed one `run_steps` row per event (~40 per case, each a Neon round trip) and re-read the full graph state after every node. Now events go to live SSE clients immediately, rows are committed at step boundaries, and the run row is refreshed only after nodes that change what the page shows. A first live UI run went from 39 s to 24 s to the review pause. | Same. |
| 65 | PDF preview | `GET /runs/{id}/pages/{n}` renders a page PNG with PyMuPDF at 2 px per PDF point, so evidence boxes (PDF points) overlay with plain percentages — no pdf.js bundle. Found while testing: the evidence locator merged every match of a value into one box (a vendor name in the header and footer covered the page); it now keeps the first occurrence plus its wrapped lines. | Plan §2b.2 highlights. |

## Phase 13: Apps platform

| # | Topic | Decision | Why |
|---|---|---|---|
| 119 | Automations as apps | The n8n workflows are replaced by built-in, installable apps modelled on DevRev snap-ins: a manifest declares typed inputs, required connections (keyrings), events, timers and hooks; the platform owns the lifecycle (DRAFT → ACTIVE ⇄ INACTIVE, or ERROR with a reason), validation on activate and on every settings change of a live app, a run log and an audit trail. Apps are code in the repo (`app/apps/builtin`), not user uploads: a marketplace of vetted apps, not arbitrary code execution. | The user asked for our own workflow platform, installable from a marketplace UI like DevRev snap-ins. |
| 120 | Secret storage | Fernet (AES-128-CBC + HMAC-SHA256) via `cryptography`, with the key in `SECRETS_KEY` (server env, never the database) and MultiFernet for rotation (`AppPlatform.rotate_secrets`). One row per secret, ciphertext only. The API returns set, hint (the last 4 characters, only for values of 12+ characters), updated_at and updated_by, and nothing else; replace and remove are explicit; every secret change is audited. Secrets are decrypted only in memory for a run or a connection test; values (and their URL-encoded forms) are scrubbed from run logs, errors and test messages. Without a key, the connection endpoints answer 503 and say how to generate one. A managed KMS or Vault was considered; not worth it on one free VM. | The user asked that API keys be stored securely. |
| 121 | Gmail access | Gmail apps use an App Password over IMAP (search with `X-GM-RAW`, fetch with `BODY.PEEK[]` so nothing is marked read before it is processed) and SMTP over SSL. OAuth would need a Google Cloud app in verification for the Gmail scopes; an App Password needs 2-Step Verification on the account and can be revoked on its own. Intake only touches unread mail sent *to* the chosen address with a PDF attached, so a busy inbox is left alone; Message-ID + file hash stop redeliveries from creating duplicates (the same `ingest_email` as the n8n route). | Free, no Google review, works with the existing intake inbox. |
| 122 | Events and timers | The pipeline emits `case.waiting_review`, `case.waiting_approval`, `case.request_info`, `case.closed` and `case.failed` (`RunService.on_event`); the platform runs every active subscriber in the background. Timers run from a 20 s scheduler loop in the API process (an interval, or daily at HH:MM IST with optional weekdays only); last-fired state is stored per app, so a restart doesn't refire a daily digest. Handlers time out after 180 s; a handler that returns `SKIP: …` logs a SKIPPED run. One API process, so no distributed locking (a known limit). | Same process model as the rest of the backend. |
| 123 | n8n migration | On start, if `N8N_BASE_URL`, `N8N_WEBHOOK_SECRET` and `SECRETS_KEY` are all set, the n8n settings are moved once into an active n8n Connector app (connection "n8n (from server settings)"), so the live site keeps working through the upgrade. The intake route accepts the app's secret and falls back to the env secret. | No gap in the live email flow. |
